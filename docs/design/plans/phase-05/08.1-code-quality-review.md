# Phase 5 — Follow & Paper Trading — Code Quality Review

> **Goal**: Consolidate findings from automated code simplification and security reviews before signing off v0.5.0.
> **Status**: ⏳ Findings documented, fixes planned
> **Review date**: 2026-06-30
> **Files reviewed**: 29 (21 new + 8 modified)

## Executive Summary

Two review agents analysed all 29 Phase 5 files:

| Agent | Total | Critical | High | Medium | Low |
|-------|-------|----------|------|--------|-----|
| Code Simplification Specialist | 36 | — | 12 | 16 | 8 |
| Security Reviewer | 42 | 2 | 12 | 19 | 9 |
| **Combined** | **78** | **2** | **24** | **35** | **17** |

**Top 5 issues to fix before release:**

1. **🔴 `trigger_follow_scoring.py` is a silent no-op** — the orchestration pipeline never computes follow scores
2. **🔴 `user_id='default'` hardcoded everywhere** — zero access control on all follow/portfolio endpoints
3. **🔴 Race conditions on paper trades** — `paper_trade_generation_loop`, `_execute_buy`, `_execute_sell` lack `FOR UPDATE`
4. **🔴 Scoring formula weights duplicated in 3 places** — service layer, ETL transformers, and tests will silently drift
5. **🔴 `volume_percentile` hardcoded to `0.5` in service layer** — API and DB return different scores for the same wallet

## 1. Bloquants Release (Critical — 2)

These must be fixed before v0.5.0 ships.

| # | File | Line | Category | Description | Fix |
|---|------|------|----------|-------------|-----|
| 1 | `app/api/v1/follow.py`, `app/api/v1/portfolio.py` | global | **Access control** | `user_id='default'` hardcoded — no authentication. Any client can read/write follows, close positions, reset portfolios. | Add authentication middleware. Replace `'default'` with the authenticated user's ID. |
| 2 | `app/main.py` | 59 | **Race condition** | `paper_trade_generation_loop` polls every 10s without `SELECT FOR UPDATE` or `SKIP LOCKED`. Two app instances can process the same alert and generate duplicate paper trades. | Add `FOR UPDATE SKIP LOCKED` to the alert query, or use a message queue for exactly-once processing. |

## 2. High Priority (24)

### 2.1 Pipelines cassées

| # | File | Issue | Fix |
|---|------|-------|-----|
| 3 | `magic/.../data_exporters/trigger_follow_scoring.py` | **No-op** — function body is `pass`. The orchestration pipeline silently skips the entire `enrichment_follow_scoring` pipeline. Follow scores are **never** computed during ETL orchestration. | Implement `trigger_pipeline('enrichment_follow_scoring')` like the other `trigger_*` exporters. |
| 4 | `magic/.../data_exporters/generate_paper_trades.py` | **No-op** — function body is `pass`. Wired into `smart_money_detection` as the final downstream block. Docstring references `paper_trade_generator.py` which doesn't exist. | Either implement real paper trade generation here (for batch mode), or remove from pipeline metadata. |

### 2.2 Duplication / Incohérence

| # | File | Issue | Fix |
|---|------|-------|-----|
| 5 | `follow_scoring.py` + `compute_follow_score.py` + tests | **Formula weights duplicated 3×** — `0.30/0.20/0.20/0.15/0.15` appear independently in service layer, ETL transformer, and unit tests. If a weight changes, 2 of 3 sites silently drift. Same problem for per-category weights and FOLLOW/WATCH/IGNORE thresholds. | Extract constants into a shared module (e.g. `app/services/scoring_constants.py`) imported by all three layers. |
| 6 | `app/services/follow_scoring.py:120` | **`volume_percentile` hardcoded to `0.5`** — line reads `+ 0.10 * 0.5` instead of querying actual `volume_percentile`. The ETL transformer correctly uses data from the DB, the test expects a parameter, but the service layer ignores it entirely. API and DB return different scores for the same wallet+category. | Replace `0.5` with the actual `volume_percentile` from the per-category query. |
| 7 | `app/main.py` vs `app/services/paper_trading.py` | **`category_filter` check duplicated** — `paper_trade_generation_loop` checks `category_filter` manually (with `json.loads` workaround for raw SQL), then `execute_copy_trade` checks it again on the ORM object. The filter runs twice per alert. | Remove the `main.py` version; let the service layer handle it. |
| 8 | `app/services/follow_scoring.py` (per-category query) | **`PERCENT_RANK` bug** — the WHERE clause filters to a single wallet (`WHERE wallet = :wallet`), so `PERCENT_RANK` always returns `0.5` instead of the actual percentile rank across all wallets. | Remove the single-wallet WHERE; compute percentile across the full dataset. |

### 2.3 Race conditions

| # | File | Line(s) | Issue | Fix |
|---|------|---------|-------|-----|
| 9 | `app/api/v1/portfolio.py` | 110 | `close_position` looks up position by ID without `FOR UPDATE` — two concurrent close calls can double-close, producing incorrect PnL and negative shares. | Use `select(PaperPosition).with_for_update().where(...)` to lock the row. |
| 10 | `app/api/v1/portfolio.py` | 162 | `reset_portfolio` deletes trades/positions then resets balance in separate statements without any lock — concurrent trade generation can insert orders between DELETE and COMMIT. | Wrap the entire reset in a single transaction with `SELECT FOR UPDATE` on the portfolio row. |
| 11 | `app/services/paper_trading.py` | 75 | `_execute_buy` selects existing OPEN position without `FOR UPDATE` — two concurrent buys for the same market/outcome can create duplicate positions or corrupt share averaging. | Add `with_for_update()` when looking up existing positions. |
| 12 | `app/services/paper_trading.py` | 143 | `_execute_sell` selects position without `FOR UPDATE` — two concurrent sell operations can oversell, making shares negative. | Add `with_for_update()` on the position SELECT. Also add a `CHECK (shares >= 0)` constraint. |
| 13 | `app/services/paper_trading.py` | 300 | `handle_market_resolution` updates positions and portfolios without locking — if called concurrently or while trades are being generated, balances become inconsistent. | Add `FOR UPDATE` on affected position rows and use a single transaction. |

### 2.4 Intégrité base de données

| # | File | Issue | Fix |
|---|------|-------|-----|
| 14 | `alembic/versions/019_add_paper_trading.py`, `app/db/models.py` | FK `PaperPosition.source_alert_id` → `alerts.id` has **no ON DELETE action**. Deleting an alert referenced by a paper position causes a foreign key violation. Same for `PaperTrade.source_alert_id`. | Add `ondelete='SET NULL'` to both foreign keys — paper trades should survive alert deletion. |
| 15 | `app/db/models.py` | No `CHECK (shares >= 0)` on `paper_positions`, no `CHECK (current_balance >= 0)` on `paper_portfolios`. Race conditions can produce negative values. | Add CHECK constraints via migration. Also add `ge=0` validation in Pydantic schemas at the API layer. |

### 2.5 Contrôle d'accès

| # | File | Line | Issue | Fix |
|---|------|------|-------|-----|
| 16 | `app/api/v1/portfolio.py` | 110, 162 | `close_position` and `reset_portfolio` have **no ownership check** — any client knowing a position UUID or portfolio ID can close/reset it. | Add a JOIN/WHERE check confirming the position's portfolio belongs to the authenticated user. |
| 17 | `app/services/paper_trading.py` | 143 | `_execute_sell` doesn't verify the sell corresponds to the original follow — if multiple follows track the same market, sells could be attributed to the wrong follow. | Match sells to their original follow source by also filtering on `followed_wallet`. |

### 2.6 Validation des entrées

| # | File | Line | Issue | Fix |
|---|------|------|-------|-----|
| 18 | `app/api/v1/follow.py` | 162 | Wallet path parameter has **no format/length validation** — `'0xdeadbeef'` passes through unchecked. Could store extremely long or invalid strings. | Validate wallet format (e.g. `0x`-prefixed hex, max 42 chars). |
| 19 | `app/api/v1/follow.py` | 141 | **No max-follows limit** — an attacker could spam unlimited follow requests, filling the `wallet_follows` table. | Add a configurable `MAX_FOLLOWS_PER_USER` check (e.g. 500). |
| 20 | `app/models/schemas.py` | 239 | `FollowCreate.category_filter` has **no validation on list values** — any arbitrary strings accepted, not just known categories. | Add a `field_validator` that checks each category against the known categories list. |
| 21 | `app/models/schemas.py` | 237 | `FollowCreate.copy_value` has **no bounds** — negative values accepted. | Add `Field(ge=0)` (or `ge=0, le=1` for proportional mode). |

### 2.7 Autres high

| # | File | Line | Issue | Fix |
|---|------|------|-------|-----|
| 22 | `app/services/follow_scoring.py` | 96+ | Scoring calculations convert to **float** for intermediate math, then back to `Decimal`. Accumulated floating-point errors can affect borderline recommendations near `0.70`/`0.35` thresholds. | Keep calculations in `Decimal` throughout. |
| 23 | `alembic/versions/018_add_wallet_follows.py` | 37 | UNIQUE constraint on `(user_id, wallet)` prevents re-following a wallet after soft-delete (`active=false`). | Change to a partial unique index: `CREATE UNIQUE INDEX ON wallet_follows(user_id, wallet) WHERE active = true`. |
| 24 | `app/tests/test_db_integrity.py` | — | **No row thresholds** for any Phase 5 tables — `COUNT(*) >= 0` is vacuously true. Pipeline bugs won't be caught. | Add meaningful `ROW_THRESHOLDS` entries for `wallet_follows`, `paper_portfolios`, `paper_positions`, `wallet_category_follow_scores`. |

## 3. Medium Priority (35)

Highlights from the medium-severity findings (full list in `phase5-simplification-review.json`):

| # | File | Issue |
|---|------|-------|
| 25 | `app/services/follow_scoring.py` | `get_follow_recommendations` makes **O(n×6) queries** — 1 initial query + 5 per wallet for 100 wallets = 601 queries just to generate "reasons" text. Batch the per-wallet queries. |
| 26 | `app/services/alert_service.py` | `get_follow_info_for_embed` hardcodes `user_id='default'` — will break when multi-user auth is added. |
| 27 | `app/main.py` | `execute_copy_trade` commits trades **one-by-one** within a batch of 20 alerts. If alert #5 fails, first 4 are already committed — partial batch, no rollback. |
| 28 | `app/main.py` | No `user_id` filter on the wallet_follows JOIN in the raw SQL query — will need refactoring for multi-user. |
| 29 | `app/services/paper_trading.py` | `update_unrealized_pnl` makes **two passes** over the same data when one would suffice. |
| 30 | `app/services/ws_manager.py` | WebSocket connections accepted **without authentication**. |
| 31 | `app/db/models.py` | `PaperPosition.status` and `PaperTrade.side` are bare `Text` columns with **no CHECK constraints** — any string accepted. Use Enum or CHECK. |
| 32 | `alembic/versions/019_add_paper_trading.py` | FK `followed_wallet` → `wallets.wallet` has no explicit `ON DELETE` — implicit `NO ACTION` may surprise. |
| 33 | `app/api/v1/portfolio.py` | `status_filter` parameter accepts arbitrary strings — `'BOGUS'` silently matches nothing. Validate against `{'OPEN', 'CLOSED', 'RESOLVED', 'ALL'}`. |
| 34 | `app/tests/test_db_integrity.py` | **F-string SQL construction** pattern for parametrized table/column names — while currently safe (hardcoded constants), the pattern is risky for future maintainers. |
| 35 | `app/services/alert_service.py` | Discord webhook URL may appear in `httpx` logs during debug/error scenarios — sensitive token exposure risk. |
| 36 | `app/services/alert_service.py` | `send_discord_alert` POST payload includes wallet info that could be intercepted if webhook is HTTP (not HTTPS). |
| 37 | `magic/.../data_loaders/load_follow_metrics.py` | SQL in `CATEGORY_METRICS_QUERY` has **no date range filter** on `trades` — could scan very large historical datasets. |
| 38 | `magic/.../transformers/compute_follow_score.py` | `float()` casts on potentially `None`/`NaN` DataFrame values — unexpected NULLs could cause `TypeError`. |
| 39 | `magic/.../transformers/compute_category_follow_scores.py` | `recency_score` uses `math.exp()` where `days` could be negative (if SQL returned 0 and subtraction went negative). |
